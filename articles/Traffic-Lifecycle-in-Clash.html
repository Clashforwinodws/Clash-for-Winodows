🗺️ 流量生命周期的全景图

当一个 TCP 数据包进入 Clash 内核，它并非简单地"进来再出去"，而是要经历一系列高度有序的处理阶段。每个阶段都有专门的数据结构和算法在运作，任何一个阶段的延迟或错误都可能影响整个连接的性能。

下面是一个 HTTPS 请求在 Clash 中经历的完整生命周期：

① 入口监听 ② DNS 解析 ③ 规则匹配 ④ 策略组决策 ⑤ 出站连接 ⑥ 数据转发 ⑦ 连接终结

这七个阶段构成了流量在 Clash 内核中的"一生"。理解每个阶段的工作机制，你就能更精准地诊断网络问题、优化连接延迟，甚至在遇到奇怪行为时快速定位根源。

💡 阅读提示： 本文假设你已具备基本的网络知识（TCP/IP、DNS、代理概念）。如果你是初次接触这些内容，建议先阅读 配置教程 和 《透视 Clash for Windows 内部》 建立基础认知。

🔌 阶段 1：流量入口 —— 四种接入方式

Clash 并非只有一个"大门"。根据你的配置，流量可以从四种不同的入口进入内核：

入口类型端口适用场景流量特征
HTTP 代理7890（默认）浏览器、支持 HTTP 代理的应用TCP only，需要应用主动配置代理
SOCKS5 代理7891（默认）更广泛的应用支持TCP + UDP，应用主动配置
Mixed 端口可配置同时兼容 HTTP 和 SOCKS5自动协议检测
TUN 模式虚拟网卡全局代理，无需应用配合TCP + UDP + ICMP，系统级拦截

无论从哪个入口进入，内核都会创建一个连接上下文（connection context），其中包含源地址、目标地址、协议类型等元数据。这个上下文将伴随流量贯穿整个生命周期，直到连接被关闭。

在 TUN 模式下，流量入口的前置步骤更为复杂——数据包需要先被虚拟网卡驱动从系统网络栈中"劫持"，然后通过 TUN 驱动 交付给用户态的 Clash 进程。这是 TUN 模式原理 中的核心环节。

🌐 阶段 2：DNS 解析 —— Fake-IP 与 Redir-Host 的分岔口

当 Clash 收到一个连接请求后，它需要知道请求的目标域名或 IP 地址。如果请求中携带的是域名（如 www.google.com），Clash 必须进行 DNS 解析。这里是流量生命周期中的第一个关键分岔口：

Fake-IP 模式：虚拟 IP 的映射游戏

在 fake-ip 模式下，Clash 不等真实 DNS 查询完成，而是立即返回一个虚拟 IP（通常位于 198.18.0.0/16 网段），并在内存中记录 域名 ↔ 虚拟 IP 的映射关系。后续当数据包到达时，Clash 通过查表还原出真实域名，再进行规则匹配。

这种方式的优势在于：

  • 零延迟： 应用程序不需要等待 DNS 查询完成，立即开始发送数据。
  • 隐私保护： 本地网络只能看到虚拟 IP，无法得知真实访问域名。
  • 规则精准： 规则匹配基于原始域名而非 IP，DOMAIN-SUFFIX 等规则可以正常工作。这与 域名匹配规则 的机制紧密相关。

Redir-Host 模式：传统 DNS 查询

在 redir-host 模式下，Clash 会向上游 DNS 服务器发起真实的查询，等待结果返回后才继续处理。这增加了延迟，但更符合传统 DNS 语义。两种模式的详细对比可参阅 缓存系统中的 DNS 缓存章节。

💡 生命周期影响： DNS 解析方式决定了后续规则匹配的数据基础。Fake-IP 让域名规则得以在 IP 层连接中正常工作，这是 Clash 规则引擎强大灵活性的基石。

🎯 阶段 3：规则匹配 —— 域名与 IP 的决策树

解析出域名（或 IP）后，流量进入规则匹配引擎。这是整个生命周期中最"智能"的阶段——Clash 需要根据你定义的规则决定这条流量应该走代理、直连，还是被直接拒绝。

规则遍历的顺序

Clash 按规则列表从上到下依次匹配。第一条命中的规则决定流量的走向。规则类型包括：

  • DOMAIN / DOMAIN-SUFFIX / DOMAIN-KEYWORD： 基于域名的精确、后缀和关键词匹配。精确匹配用哈希表，后缀匹配用前缀树——详细的底层实现见 规则匹配精讲。
  • GEOIP / IP-CIDR： 基于目标 IP 的地理位置或网段匹配。
  • MATCH： 兜底规则，匹配所有未命中前面规则的流量。

缓存命中：规则匹配的加速器

对于重复访问的域名，Clash 会将匹配结果缓存在 规则匹配缓存 中，避免每次请求都遍历完整的规则树。这意味着对于长连接（如视频流、WebSocket），规则匹配的开销几乎可以忽略。

匹配结果与策略组关联

规则匹配的最终产物是一个策略组名称——例如 PROXY、DIRECT 或 REJECT。这个名称将作为下一个阶段的输入。

🧪 阶段 4：策略组决策 —— 节点选择的逻辑

如果规则决定流量走代理，Clash 还需要从策略组中选择一个具体的代理节点。策略组的类型决定了选择逻辑：

策略组类型选择逻辑典型场景
select用户手动指定固定出口、调试
url-test自动选择延迟最低的节点日常浏览、视频
fallback按顺序尝试，第一个可用即选高可用场景
load-balance轮询或哈希分配大流量下载

策略组的决策结果会被缓存一段时间（interval 参数控制），在缓存有效期内不会重新测试或切换。这就是 策略组缓存 的工作机制。更深入的分析见 《策略组完全解析》。

选定节点后，Clash 会检查是否有已建立的可用连接可以复用。如果连接池中存在到该节点的空闲连接，Clash 会直接使用它，跳过接下来的出站连接建立阶段。连接复用的详细机制见 连接复用章节。

🔐 阶段 5：出站连接 —— 协议封装与加密

如果没有可复用的连接，Clash 需要与代理节点建立一条新的 TCP 连接。这个阶段是延迟的主要来源之一，尤其是在跨国网络中。

连接建立与 TFO 优化

标准的 TCP 连接需要完成三次握手，消耗 1 个 RTT。如果节点配置了 fast-open: true 且操作系统支持，Clash 会使用 TCP Fast Open 在 SYN 包中直接携带数据，将连接建立延迟压缩到接近零。

协议封装

TCP 连接建立后，Clash 根据节点类型将应用层数据封装到对应的代理协议中：

  • Shadowsocks： AEAD 加密后直接通过 TCP 传输。
  • VMess / VLESS： 使用自定义的认证和加密协议。
  • Trojan： 伪装成 HTTPS 流量，通过 TLS 隧道传输。

每种协议的封装和解封装过程都是 CPU 密集型的。Clash 使用 Go 语言的加密库进行高效的加解密操作，这也是它能在低端设备上保持高性能的原因之一。协议层的更多讨论见 《TCP 与 UDP 深度对比》。

UDP 流量的特殊处理

如果流量是 UDP（例如 DNS 查询、游戏数据包），Clash 需要先在 UDP NAT 表 中建立会话状态，然后将 UDP 数据报封装到协议的 UDP 传输通道中。这与 TCP 的连接模型有本质区别，详见 TCP 与 UDP 对比。

🔄 阶段 6：数据转发 —— 双向流转的细节

连接建立并完成协议握手后，Clash 进入数据转发阶段。这一阶段持续整个连接的生存期，是流量吞吐的主要环节。

双向数据流

Clash 在客户端和代理节点之间维护两个方向的数据流：

  • 上行（客户端 → 节点）： 从入口连接读取明文数据，加密/封装后写入到出站连接。
  • 下行（节点 → 客户端）： 从出站连接读取加密数据，解密/解封装后写回入口连接。

这两个方向的数据流动通常是异步并行的，Clash 使用 goroutine 来处理，确保一个方向的阻塞不会影响另一个方向。

缓冲与流控

为了提高吞吐量，Clash 使用了内部的发送和接收缓冲区。缓冲区的大小和策略会影响内存占用和延迟。对于大文件下载，较大的缓冲区能提高效率；对于实时游戏，较小的缓冲区能减少延迟。

TUN 模式下的特殊路径

在 TUN 模式下，数据转发涉及额外的内存复制——数据需要从内核态的虚拟网卡复制到用户态的 Clash 进程，再写入到出站 socket。这个过程中的零拷贝优化是 TUN 驱动性能 的关键关注点。

🔚 阶段 7：连接终结 —— 超时、清理与资源回收

当数据传输完成，或连接空闲超时，Clash 需要正确关闭连接并释放所有相关资源。这个阶段虽然不直接影响用户体验，但直接影响内核的长期稳定性和内存占用。

TCP 连接关闭

对于 TCP 连接，Clash 遵循标准的四次挥手流程。客户端发送 FIN 后，Clash 会继续转发对端的数据直到也收到 FIN。如果连接异常中断（如网络断开），Clash 通过超时机制检测并清理。

UDP 会话清理

UDP 没有连接关闭的概念。Clash 依赖 UDP NAT 表 的空闲超时来清理会话。当会话在指定时间内没有数据流动时，对应的 NAT 条目会被移除，释放资源。

连接池的回收

对于 TCP 连接，Clash 不会立即关闭到代理节点的连接，而是将其放回 连接池 中，等待后续请求复用。连接池中的连接会保持 Keep-Alive 状态，直到空闲超时后才真正关闭。

Fake-IP 映射的释放

当连接关闭后，Fake-IP 映射表会检查该域名是否仍有其他活动连接。如果没有，映射条目可能被标记为可回收，在内存紧张时被清除。这部分内容在 缓存失效策略 中有详细讨论。

⚡ 全链路优化：缓存、复用与 TFO

理解了完整的生命周期后，我们可以从全局视角审视各个优化手段如何协同工作：

优化技术作用阶段主要收益相关文章
DNS 缓存（Fake-IP）阶段 2消除 DNS 查询延迟缓存系统
规则匹配缓存阶段 3减少 CPU 开销缓存系统
策略组缓存阶段 4避免重复延迟测试策略组指南
TCP Fast Open阶段 5消除 1 个 RTT 的握手延迟TFO 指南
连接复用阶段 5-6避免重复握手缓存系统
规则精简阶段 3减少匹配遍历时间规则集维护

这些优化手段覆盖了生命周期中的每一个阶段。一个经过良好调优的 Clash 配置，应该在每个阶段都充分应用了合适的优化。如果你想进一步优化配置，推荐阅读 《大型配置文件管理指南》。

🔍 调试与追踪：如何观测生命周期

了解理论之后，你需要工具来实际观测流量的生命周期。以下是几个实用的调试方法：

1. Debug 日志

设置 log-level: debug，Clash 会记录每个请求经过的关键阶段：

[DEBUG] accept connection from 127.0.0.1:54321
[DEBUG] dns resolve domain www.google.com -> fake-ip 198.18.0.1
[DEBUG] match rule: DOMAIN-SUFFIX,google.com,PROXY
[DEBUG] proxy group PROXY selected node: 日本节点
[DEBUG] dial tcp 203.0.113.1:8388 (日本节点)
[DEBUG] connection established, start forwarding

这些日志清晰地展示了每个请求的生命周期轨迹。

2. Clash API

通过 GET /connections 可以查看当前所有活动连接，包括它们命中的规则、使用的节点、实时流量速度等。这是观测数据转发阶段的绝佳工具。

3. 抓包分析

使用 Wireshark 或 tcpdump 可以捕获真实的数据包，观察协议封装的实际形态。在 TUN 模式下，你甚至可以看到虚拟网卡上的原始 IP 包。相关的分析技巧见 拆分隧道指南 中的调试部分。

4. 性能剖析

如果怀疑某个阶段存在性能瓶颈，可以使用 Go 的 pprof 工具对 Clash 进程进行 CPU 和内存剖析。这对于内核级调试尤其有用。

📊 实战案例：一次慢请求的解剖

假设你发现访问某个网站时延迟异常高。通过理解流量生命周期，我们可以系统地排查问题：

  1. 检查入口阶段： 浏览器是否正确配置了代理？TUN 模式是否正常工作？
  2. 检查 DNS 解析： Fake-IP 映射是否正常？日志中 DNS 解析耗时多少？
  3. 检查规则匹配： 该域名是否意外命中了错误的规则？
  4. 检查策略组： 当前选择的节点延迟如何？是否需要切换到更快的节点？
  5. 检查出站连接： 到节点的连接建立是否缓慢？TFO 是否生效？
  6. 检查数据转发： 吞吐量是否达到预期？是否有大量重传？

这种系统化的排查方法比盲目尝试配置修改要高效得多。如果你在排查过程中遇到了困难，可以参考 常见问题页面 中的网络诊断章节，或 订阅排障手册 中关于连接超时的分析。

📌 总结：理解生命周期即掌控代理

从入口监听到连接终结，流量在 Clash 内核中经历了一个精密而复杂的生命周期。每个阶段都有其独特的数据结构、算法和优化策略。当你真正理解了这个生命周期：

  • 排障更精准： 遇到问题时能快速定位到具体阶段。
  • 优化更有效： 知道每个优化手段作用于哪个阶段。
  • 配置更合理： 理解参数背后的机制，而非盲目复制。
  • 架构更清晰： 对 Clash 的整体设计理念有深入的把握。

这篇文章是 Clash 技术体系的"总纲"。在此基础上，你可以根据兴趣深入每个具体领域：规则匹配的细节、缓存系统的优化、连接建立的加速、TUN 模式的原理。当你将这些知识融会贯通，就能真正成为 Clash 的高级用户。
