🏗️ 整体架构：三层进程模型

Clash for Windows 并不等同于 Clash 核心。它是一个桌面壳层，负责提供用户界面、系统集成和便捷的配置管理。其内部由三个主要进程协同工作：

层级技术栈主要职责
GUI 前端Electron (Chromium + Node.js)渲染窗口、展示节点列表、策略组切换、日志查看
桥接层Node.js (主进程)管理 Clash 子进程生命周期、读写配置文件、提供 RESTful API、处理系统托盘
代理核心Go (Clash / Clash Meta)规则匹配、协议解析、数据包转发、DNS 解析、TUN 驱动交互

用户看到的每一个界面操作，最终都会通过 IPC（进程间通信）传递到 Node.js 主进程，再由主进程通过 HTTP API 或信号控制 Go 核心。反过来，核心的实时状态（如流量、日志）也会异步推送给 UI 层。

💡 设计哲学： 这种分离架构使得界面崩溃不会影响代理核心继续工作；同时，核心专注于高性能网络处理，而 UI 可以灵活定制。

🖥️ Electron 前端：GUI 的状态同步

CFW 的界面本质上是一个运行在 Electron 中的 Web 应用。它使用 React 或 Vue 等前端框架构建，通过 WebSocket 或轮询方式从 Node.js 主进程获取核心数据。当你点击“代理”页面时，前端会发起 HTTP 请求到 http://127.0.0.1:9090（Clash 内置 API），拉取节点列表和策略组信息，并展示为可交互的卡片。

策略组的切换操作触发了以下流程：

  1. 用户在 UI 中选择一个新的节点。
  2. 前端调用 PUT /proxies/{group} API，传递所选节点名称。
  3. Node.js 主进程接收请求，直接转发给 Go 核心的 HTTP 服务器。
  4. Go 核心立即更新内存中的策略组状态，后续的流量就会使用新的节点。
  5. UI 通过定时轮询或 WebSocket 事件获得状态变更，更新显示。

这种设计让 UI 成为核心状态的一个“反射”，即使关闭界面，代理依然正常运行。

⚙️ Node.js 桥接层：配置与信号

Node.js 主进程是 CFW 的“大脑”。它负责以下关键任务：

  • 启动与守护： 以子进程方式启动 clash.exe（或 Meta 核心），监控其运行状态，崩溃后自动重启。
  • 配置管理： 将用户通过 UI 编辑的配置写入 YAML 文件，并通知核心重新加载（发送 SIGHUP 信号或调用 PUT /configs API）。
  • 系统代理设置： 调用 Windows API（如 WinINet）修改系统代理，让浏览器流量自动进入 Clash 的 SOCKS5/HTTP 端口。
  • TUN 模式管理： 安装/卸载 Wintun 驱动，创建虚拟网卡，并配置路由表。

Node.js 主进程与 Go 核心之间的通信主要依靠 HTTP REST API 和 进程信号。API 地址默认为 http://127.0.0.1:9090，提供丰富的端点用于查询和修改核心状态。

// 示例：通过 API 获取当前所有代理节点
GET http://127.0.0.1:9090/proxies

// 切换策略组中的节点
PUT http://127.0.0.1:9090/proxies/PROXY
{"name":"日本节点"}

🧠 Clash 核心：Go 语言的高效引擎

Go 编写的内核是整个系统的性能核心。它启动后即开始监听多个端口：

  • HTTP 代理 (7890)： 接收浏览器等应用发出的 HTTP CONNECT 请求。
  • SOCKS5 代理 (7891)： 处理支持 SOCKS5 协议的应用流量。
  • API 服务 (9090)： 提供 RESTful 接口供前端和外部工具查询控制。
  • 混合端口 (mixed-port, 可选)： 同时支持 HTTP 和 SOCKS5。
  • TUN 接口： 在系统层面拦截所有 IP 包。

内核内部维护着一个 规则匹配树 和 连接池。对于每一个进入的请求，它会经历 DNS 解析、规则匹配、代理协议封装等步骤。这些操作全部在 Go 的 goroutine 中并发处理，以保证极高的吞吐量和极低的资源占用。

🔗 进程间通信：HTTP API 与信号管道

CFW 的 IPC 可分为两类：请求-响应 和 事件推送。

请求-响应模式 (REST API)

用于主动查询和修改核心状态，如获取流量统计、切换节点、更新配置等。所有请求均由 Node.js 主进程发起，Go 核心响应 JSON 数据。

事件推送 (WebSocket / Server-Sent Events)

对于实时日志、连接变化、带宽使用等高频信息，CFW 使用 WebSocket 连接到核心的 /ws 端点。Go 核心会将每条日志、每个连接事件实时推送给前端，避免了频繁轮询带来的性能浪费。

信号控制

除了 API，Node.js 还可以向 Go 进程发送操作系统信号。例如，发送 SIGHUP 会触发配置重载，而无需重启整个核心。

📦 一次数据包的完整旅程

假设用户在浏览器中访问 https://www.google.com，并且已开启系统代理模式。以下是数据包的详细路径：

  1. 浏览器根据系统代理设置，将 HTTP CONNECT 请求发送到 127.0.0.1:7890。
  2. Clash 核心在 7890 端口上监听，接收到连接后解析目标域名 www.google.com。
  3. DNS 模块根据配置决定解析方式：Fake-IP 返回虚拟 IP 并记录映射；Redir-Host 则进行真实 DNS 查询。
  4. 规则引擎从第一条规则开始匹配，假设命中 DOMAIN-SUFFIX,google.com,PROXY，选定策略组 PROXY。
  5. 策略组 PROXY 根据设置（可能是手动选择或 url-test）确定最终使用的节点。
  6. 核心通过该节点的代理协议（如 Shadowsocks）封装请求，并将数据包发送到远程服务器。
  7. 远程服务器解密、转发请求到真正的 Google 服务器，获得响应后原路返回。
  8. Clash 核心接收到响应数据，将其通过 7890 端口传回给浏览器。
  9. 浏览器渲染页面，用户看到内容。

如果开启了 TUN 模式，第 1 步将变为：所有发往外网的 IP 包被虚拟网卡截获，直接交给 Clash 内核处理，不再经过系统代理设置。具体的 TUN 数据包处理细节可参阅 《Windows TUN 驱动深度解析》。

🔄 配置的生命周期：从文件到热加载

CFW 的配置文件（通常为 YAML 格式）在多个层级中被处理：

  • 持久化： Node.js 主进程将用户在 UI 中的修改（如节点排序、策略组名称）写入磁盘上的 config.yaml。
  • 加载： Go 核心启动时读取配置文件，解析 YAML 并构建内部数据结构。
  • 热更新： 当配置文件被修改（通过 UI 或外部编辑器），Node.js 发送 PUT /configs?force=true 请求。Go 核心重新解析 YAML，并更新运行中的规则、策略组和代理列表，无需断开已有连接。
  • Provider 动态更新： 对于 proxy-providers 和 rule-providers，Go 核心会定期从 URL 拉取，单独更新而不影响其他配置。

这种机制使得你可以随时调整代理规则而不中断网络连接。结合 《大型配置文件管理指南》 中介绍的模块化拆分，配置热加载的效率会更高。

⚡ 性能视角：为什么 CFW 如此轻量？

与其他基于 Python (ShadowsocksR) 或 Java (V2RayN) 的客户端相比，CFW 的资源占用显著更低，这得益于：

  • Go 语言的并发模型： Goroutine 的开销极小，单个代理连接仅占用约 4KB 内存，支持数万并发。
  • Electron 的懒惰加载： 前端仅在窗口打开时消耗 CPU 和内存，关闭后只保留轻量的托盘进程。
  • 零拷贝技术： 在 TUN 模式下，内核到用户态的数据传输使用共享内存，减少内存复制。
  • 高效的规则引擎： 使用 trie 树和哈希表加速域名匹配，避免线性扫描。

若希望进一步优化，可以阅读 《TCP 与 UDP 深度对比》 和 《Clash 与 HTTP/3》，从协议和传输层继续挖掘性能潜力。
